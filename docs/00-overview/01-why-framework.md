# 1. なぜエージェントフレームワークが必要か（4分）

## 1-1. LLM API を直接呼ぶだけでは足りない

「東京の天気を調べて、旅行の持ち物を提案して」という依頼を考えます。LLM は言葉を生成できますが、**今日の東京の天気は知りません**。
学習データは過去のものであり、外部システムにアクセスする手段も持たないためです。

そこで使うのが**ツール呼び出し**（function calling）です。流れはこうなります。

1. アプリが LLM に「使える道具の一覧」（天気を調べる関数の名前・説明・引数の形）を一緒に渡す
2. LLM は答えを直接返す代わりに「`weather` を `{ city: "Tokyo" }` で呼んでほしい」と要求を返す
3. **アプリ側**が実際に天気 API を叩き、結果を LLM に戻す
4. LLM が結果を踏まえて続きを考える。必要ならまた別の道具を要求する
5. もう道具が要らないと判断したら、最終的な文章を返す

この **2〜4 を必要なだけ繰り返す仕組みが「エージェント」** です。LLM が「次に何をするか」を自分で決める点が、単発の API 呼び出しとの決定的な違いです。

## 1-2. 自分で書くと何が必要になるか

このループを自前で実装すると、本質でない作業が大量に発生します。

| 自前で書く必要があるもの | 内容 |
|---|---|
| ツール定義の変換 | 関数の引数の形を、各 LLM プロバイダが要求する JSON Schema に変換する |
| ループ制御 | 何回まで繰り返すか、いつ止めるか、無限ループをどう防ぐか |
| 会話履歴の管理 | 過去のやり取りをどこに保存し、どこまでを次の呼び出しに含めるか |
| 入出力の検証 | LLM が返した引数が本当に期待した型か検証する（LLM は間違った形で返すことがある） |
| エラー処理 | API のレート制限、タイムアウト、ツール実行失敗時の再試行 |
| プロバイダ差の吸収 | OpenAI と Google と Anthropic でリクエスト・レスポンスの形が違う |
| 可観測性 | どのプロンプトで何トークン使い、どのツールが何秒かかったかを記録する |
| 品質評価 | 出力が良くなったか悪くなったかを、変更のたびに測る手段 |

エージェントフレームワークは、この一覧を**すべて引き受けるための道具**です。Mastra もその一つです。

## 1-3. 用語の整理

以降で繰り返し出てくる言葉を先に揃えておきます。

| 用語 | 意味 |
|---|---|
| **LLM** | 大規模言語モデル。Gemini、GPT、Claude など |
| **ツール呼び出し** | LLM が「この関数をこの引数で呼んで」と要求する仕組み。実行するのはアプリ側 |
| **エージェント** | LLM に道具を持たせ、次の行動を LLM 自身に決めさせる仕組み。**手順は事前に決まっていない** |
| **ワークフロー** | 実行順序を人間が事前に決めて記述する多段処理。**手順が決まっている** |
| **RAG** | 社内文書などを検索してからLLMに答えさせる手法（Retrieval-Augmented Generation） |
| **MCP** | LLM と外部ツールをつなぐ共通規格（Model Context Protocol）。対応ツールをそのまま繋げる |
